### T7 — the SQLite write-lock hold across model calls is fixed (commit `2b3857a`)

- **Finding (an external audit; validated here claim-by-claim):** while a multi-minute REAL `analyze`
  job ran, every other write answered HTTP `500 sqlite3.OperationalError: database is locked`. The
  audit's live evidence: `/v1/meetings/{id}/status` at 12:18:38 and `/v1/auth/login` (`UPDATE
  auth_tokens SET last_used_at`) at 12:18:55 UTC both `500` during the run, and login answered `200`
  the moment the run finished (12:20:16). Our own final wave matched it (an `UPDATE auth_tokens` `500`
  during the 387 s job).
- **Validated mechanism (read in code):** `db/base.py` set only `PRAGMA foreign_keys=ON` — no
  `journal_mode=WAL` and no `busy_timeout`, so pysqlite's default 5 s lock timeout applied; and in
  `pipeline/analyze.py` `_new_run()`'s `flush()` opened the write transaction, while
  `context.progress()` / `context.event()` commit only AFTER each model call — so EVERY
  `analyzer.complete_json()` ran inside an open write transaction and pinned SQLite's write lock for
  the entire multi-minute call. Postgres is unaffected (MVCC), and CI never caught it because the
  mock/stub analyzers return instantly.
- **The fix (two parts, both required):** (1) `analyze.py` — one `context.session.commit()` at the top
  of the `analyze_job.call` helper, immediately after `context.check_cancelled()` and before
  `analyzer.complete_json(...)`, so no model call is ever inside a write transaction (safe because the
  sessionmaker is `expire_on_commit=False`); (2) `db/base.py` — the `_fk_on` connect hook became
  `_sqlite_pragmas`, executing `PRAGMA foreign_keys=ON`, `PRAGMA journal_mode=WAL` and
  `PRAGMA busy_timeout=30000` (readers never block the writer, a brief residual burst retries instead
  of erroring).
- **RED (before the fix), observed:** `./.venv/Scripts/python.exe -m pytest
  tests/integration/test_analysis_jobs.py::test_analyze_does_not_pin_the_write_lock_across_a_model_call
  -q` → `1 failed in 7.43s`, the failure being
  `sqlalchemy.exc.OperationalError: (sqlite3.OperationalError) database is locked` /
  `[SQL: UPDATE jobs SET progress=?, updated_at=CURRENT_TIMESTAMP WHERE jobs.id = ?]`, raised out of the
  `session_scope` commit — the lock really was pinned by the parked model call, and it only failed after
  the ~5 s default timeout.
- **GREEN (after the fix), observed:** the lock test plus the new pragma test →
  `2 passed in 1.00s` (the concurrent write commits while the "model call" is still parked); the full
  suite → `214 passed, 2 skipped in 46.75s` (baseline 212 + the 2 new tests);
  `ruff check src tests` → `All checks passed!`; `ruff format --check src tests` →
  `108 files already formatted`.
- **Files:** `backend/src/mvb/pipeline/analyze.py`, `backend/src/mvb/db/base.py`,
  `backend/tests/integration/test_analysis_jobs.py`, `backend/tests/unit/test_sqlite_engine.py`.
