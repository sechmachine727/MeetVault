# PROGRESS_2026-10-08

Owner: sechmachine

## Objective

Fix CUDA inference falling back to CPU with no visible sign, and surface a UI warning when a requested GPU is not used. Done when whisper.net selects CUDA on a machine with a supported NVIDIA GPU, the picker never offers CUDA that cannot load, a fallback shows as a warning on the Live page, and the work sits on a branch with a pull request rather than a direct push to main.

## Work log

### 02:55 - Branch created and root cause found

- **Changed or found:** CUDA was not a GPU problem. whisper.net gates the CUDA runtime on `CudaHelper.IsCudaAvailable`, which loads `cudart64_13` by bare name through `NativeLibrary.TryLoad`. That search covers the exe directory, System32 and PATH, never `runtimes\cuda\win-x64` where the app stages it, so the probe fails on every machine and transcription falls back to CPU.
- **Evidence:** whisper.net 1.9.1 source (`LibraryLoader/CudaHelper.cs`, `LibraryLoader/NativeLibraryLoader.cs`); `publish\win-x64\MeetVault.deps.json` has no cudart entry; `cudart64_13.dll` present only under `runtimes\cuda\win-x64`; user log `app (1).log` shows `CUDA runtime Cuda is not available.` and `Cuda driver for Cuda is not available or no cuda device is identified.` before `loaded=Cpu`.
- **Files:** none.
- **Decision:** Fix at the packaging and probe layers, not by preloading in `App.xaml.cs`, so the fix holds for both the portable publish and the MSIX.
- **Next:** reproduce on this machine.

### 04:45 - Vulkan diagnosed: cached native, wrong device index, no compute truth

- **Changed or found:** CUDA is verified working (RTX 4070, `loaded=Cuda`, ~320-480 ms/window). Vulkan has three defects. (1) whisper.net loads the native DLL once per process, so switching CPU/CUDA then Vulkan reuses the first native; the user's 04:02 'Vulkan' run actually ran CUDA, not Vulkan. (2) `GpuProbe` numbered Vulkan devices over the raw loader order, but ggml-vulkan keeps only discrete and integrated GPUs (`ggml_vk_device_is_supported`), so a filtered-out device shifts whisper's `gpu_device`. (3) `LoadedBackend` reports which DLL loaded, not the device whisper initialized, so a GPU DLL with CPU compute showed no warning and the engine line overstated the accelerator.
- **Evidence:** `app (3).log`: 04:00 `loaded=Cuda`, then 04:02 `requested Vulkan but the runtime loaded Cuda`. ggml-vulkan source: `device_indices.push_back(i)` only for `eDiscreteGpu || eIntegratedGpu` and `ggml_vk_device_is_supported`. whisper.cpp `whisper_backend_init_gpu` counts GPU/IGPU entries and logs `using X backend` / `no GPU found`.
- **Files:** `src/MeetVault.Core/GpuProbe.cs`, `src/MeetVault.Core/WhisperTranscriber.cs`, `src/MeetVault/Views/LivePage.xaml.cs`, `tests/MeetVault.Core.Tests/GpuProbeTests.cs`, `AGENTS.md`.
- **Decision:** Mirror ggml's device filter when numbering the Vulkan picker, and parse whisper's own `using X backend` / `no GPU found` line for the real compute device so the engine line and the fallback warning reflect it.
- **Next:** re-test Vulkan with the Intel iGPU and read the new `whisper_backend_init_gpu` lines; the index fix is latent on this exact machine (its Vulkan list already matched ggml's) so the log is what resolves the Intel case.
